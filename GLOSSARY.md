# Словарь терминов проекта

Пополняется по ходу работы. Формат: термин [предметная область] — определение.

## ИИ и RAG

- RAG [ИИ-архитектура] — Retrieval-Augmented Generation: модель отвечает на вопрос не из своей памяти, а по найденным фрагментам ваших документов. Отсюда и точные ответы со ссылками на источники.
- Corrective RAG [ИИ-архитектура] — усложнение RAG: перед генерацией ответа LLM проверяет, релевантны ли найденные фрагменты, и при необходимости расширяет запрос и ищет заново (у нас — до 2 раз).
- LLM [ИИ] — большая языковая модель, «мозг», генерирующий текст. В проекте — локальная Qwen2.5-3B через Ollama, без платных API.
- Эмбеддинг [ИИ] — превращение текста в вектор чисел так, что похожие по смыслу тексты дают близкие векторы. Основа поиска по смыслу.
- Вектор [ИИ-поиск] — упорядоченный набор чисел, представляющий текст в «математическом» виде. Сравнивая векторы, машина сравнивает смыслы.
- Косинусная близость [математика поиска] — мера похожести двух векторов через угол между ними (1.0 — одинаковое направление). Альтернатива L2 — расстояние между концами векторов; для нормализованных векторов дают одинаковый порядок.
- Токен [ИИ] — минимальная единица текста для модели (часть слова, слово или знак). Также единица измерения контекста и стоимости.
- Контекст (окно контекста) [ИИ] — объём текста, который модель может «держать в голове» за один вызов. Поэтому в ответ подаём только топ-6 чанков, а не все файлы.
- Промпт [ИИ] — текст-обращение к модели: инструкция + данные. Качество промпта сильно влияет на качество ответа.
- Чанк [RAG] — кусок документа ~1200 символов, единица индексации и поиска; помнит свой источник и позицию в файле.
- Чанкинг [RAG] — разбивка документов на чанки. Код режется по границам функций, текст — по абзацам.
- Перекрытие, overlap [обработка документов] — намеренное дублирование 200 символов между соседними чанками, чтобы мысль на границе разреза не потерялась.
- Сплиттер [обработка документов] — инструмент разрезки текста на части; наш — RecursiveCharacterTextSplitter из LangChain (режет по абзацам → предложениям → словам).
- Метаданные [данные] — данные о данных: у чанка это файл-источник, номер куска, тип документа. Дают источники в ответах.
- Источники, sources [RAG] — список файлов, из которых собран ответ; требование задания к инструменту ask_question.
- Индексация [RAG] — обработка папки в базу: скан → чтение → чанки → эмбеддинги → ChromaDB. Выполняется инструментом index_folder.
- Retriever [RAG] — модуль, находящий релевантные чанки по запросу. Наш — гибридный (BM25 + вектор → RRF).
- Retry-цикл [RAG] — повтор поиска с расширенным запросом, если первый не нашёл релевантного. В проекте максимум 2 повтора.

## Поиск

- BM25 [поиск] — классический алгоритм поиска по словам: документ релевантнее, если слова запроса часто в нём встречаются, причём редкие слова весят больше. Силён на точных терминах и идентификаторах.
- IDF [поиск] — «обратная документная частота» внутри BM25: чем реже слово в корпусе, тем оно информативнее и больше весит.
- Корпус [поиск] — набор документов, по которому идёт поиск (вся проиндексированная база).
- Токенизация [поиск] — разбиение текста на токены-слова для BM25; у нас `re.findall(r"\w+", ...)` — работает и с кириллицей.
- Гибридный поиск [поиск] — одновременное использование поиска по словам (BM25) и по смыслу (векторы) со слиянием результатов. Отвечает и на точечные, и на смысловые вопросы.
- RRF [поиск] — Reciprocal Rank Fusion: документу начисляется 1/(k + позиция) в каждом списке результатов, суммы складываются. Документ, найденный обоими методами, ранжируется выше.
- Sparse / dense retrieval [поиск] — два семейства поиска: sparse — по словам (BM25), dense — по векторам («плотным» представлениям смысла).

## Python и библиотеки

- uv [инструмент] — быстрый менеджер Python-пакетов: ставит зависимости и фиксирует их точные версии. Аналог npm для JavaScript.
- Виртуальное окружение, .venv [Python] — изолированная папка с пакетами конкретного проекта, чтобы версии не конфликтовали с другими проектами.
- Зависимость [Python] — сторонняя библиотека, которую использует проект; перечислена в pyproject.toml и скачивается с PyPI.
- pyproject.toml [Python] — единый файл описания проекта: зависимости, инструменты, настройки (pytest, ruff).
- Lock-файл, uv.lock [Python] — фиксация точных версий всех пакетов (включая зависимости зависимостей), чтобы у всех было одинаковое окружение.
- Импорт [Python] — подключение кода библиотеки или своего модуля в файле: `from x import Y`.
- dataclass [Python] — декоратор для класса-«контейнера данных» без логики: короткая запись, поля с типами.
- Protocol [Python] — «джентльменский договор» о методах класса: любой объект с нужными методами подходит (у нас Embedder и LLM).
- Фабрика [паттерн] — функция, создающая нужный объект по условию; у нас create_embedder() выбирает провайдера эмбеддингов по конфигу.
- Обёртка / адаптер [паттерн] — класс, переводящий чужой API на язык проекта; изолирует зависимость в одном файле (VectorStore над ChromaDB).
- Upsert [БД] — «update or insert»: запись с таким id обновляется, если существует, иначе создаётся.
- LangChain [библиотека] — набор инструментов для работы с документами и LLM: лоадеры, сплиттеры, клиенты моделей.
- TextLoader [LangChain] — загрузчик текстовых файлов из LangChain; читает файл в «документ» с полем page_content.
- LangGraph [библиотека] — оркестратор LLM-цепочек как графа шагов с условными переходами; на ней построен наш Corrective RAG.
- FastMCP [библиотека] — Python-фреймворк для MCP-серверов: инструмент объявляется функцией с описанием.
- ChromaDB [БД] — встраиваемая векторная база: хранит чанки и векторы, ищет ближайшие. In-process, без отдельного сервера.
- In-process [архитектура] — библиотека работает внутри нашего процесса, а не отдельным сервисом; данные всё равно персистентны на диске.
- pydantic-settings [библиотека] — читает настройки из переменных окружения/.env в типизированный класс Settings.

## Инфраструктура

- MCP [протокол] — Model Context Protocol: стандарт подключения внешних инструментов к ИИ-агенту в IDE (Copilot, Claude). Наш сервер отдаёт 4 инструмента.
- Ollama [инструмент] — программа для запуска локальных LLM как сервиса; по HTTP отдаёт ответы модели и эмбеддинги.
- Qwen2.5-3B / nomic-embed-text [модели] — наша LLM (3 млрд параметров) и модель эмбеддингов соответственно; обе крутятся в Ollama.
- Docker [инфраструктура] — упаковка приложения с окружением в контейнер, запускаемый одинаково на любой машине.
- Docker Compose [инфраструктура] — описание мульти-контейнерного состава (сервер + Ollama + загрузка моделей) одной командой `docker compose up`.
- Streamable HTTP [транспорт] — режим работы MCP-сервера как долгоживущего веб-сервиса по http://localhost:8000/mcp; выбран вместо stdio ради Docker.
- CI [инфраструктура] — Continuous Integration: автозапуск линтера и тестов при каждом пуше (GitHub Actions).

## Разработка и тестирование

- TDD [разработка] — Test-Driven Development: сначала тест (падает), потом реализация (тест зелёный), потом рефакторинг.
- Юнит-тест [тестирование] — тест одной функции/класса в изоляции; быстрый и точный.
- e2e-тест [тестирование] — end-to-end: проверка сценария целиком (например, MCP-инструменты через клиента).
- Пиннинг-тест [тестирование] — тест, закрепляющий неочевидное поведение (например, «после пересборки BM25 старые термины не ищутся»).
- Фикстура [тестирование] — подготовленные данные/объекты для теста (у нас: tmp_path, FakeEmbedder).
- Fake-объект [тестирование] — подмена реальной зависимости детерминированной (FakeLLM отвечает по списку); тесты идут быстро и без сети.
- Линтер, ruff [инструмент] — статическая проверка кода: стиль, ошибки, импорты; ruff — быстрый Python-линтер.
- Коммит [git] — зафиксированный снимок изменений с сообщением; история проекта.
- Ревью кода [разработка] — проверка кода другим исполнителем; у нас двухступенчатое: соответствие спеке, затем качество.
- Субагент [ИИ-разработка] — отдельный агент со своим контекстом, выполняющий одну задачу и возвращающий отчёт; главная сессия координирует.
- Скилл [ИИ-разработка] — подключаемый процесс-инструкция для агента (плагин superpowers: планирование, TDD, ревью).
- DONE_WITH_CONCERNS [ИИ-разработка] — статус отчёта субагента «сделано, но есть сомнения» — сигнал контроллеру разобраться перед приёмкой.
