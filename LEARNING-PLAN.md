# Простой план проекта (обучающий)

Этот план — для тебя. Он объясняет, ЧТО мы делаем и ЗАЧЕМ, простыми словами.
Детали реализации — в PLAN.md (технический план).

**Как работаем:** идём по пунктам. После каждого пункта я спрашиваю: «Что занести в REPORT.md?» — ты диктуешь своими словами, я оформляю и записываю. Непонятное спрашивай сразу.

## Этап 1. Фундамент

**п.1. Установить uv и создать каркас проекта.**
uv — это менеджер Python-пакетов (как npm для JavaScript). Нужен, чтобы быстро ставить библиотеки и зафиксировать их версии — чтобы у преподавателя всё запустилось точно так же, как у нас.

**п.2. Конфигурация (config.py).**
Все настройки (имя модели, пути, порты, лимиты) в одном месте, читаются из файла .env. Это нужно, чтобы в коде не было хардкода — это прямой критерий оценки.

## Этап 2. Индексация документов

**п.3. Загрузчик файлов (loaders).**
Сканирует папку и читает 7 форматов: .md, .txt, .py, .js, .ts, .json, .yaml. Это нужно, чтобы принимать любые документы пользователя.

**п.4. Разбивка на чанки (chunking).**
Длинные документы режутся на куски ~1200 символов. Поиск и LLM работают с короткими кусками, а не с целыми файлами. Каждый чанк помнит, из какого файла и какого места он пришёл — это даёт «источники» в ответах.

**п.5. Эмбеддинги (embedder).**
Превращают текст в вектор из чисел: похожие по смыслу тексты → близкие векторы. Это основа поиска ПО СМЫСЛУ («как работает магия» найдёт «заклинания»). Два провайдера: встроенный в ChromaDB или Ollama (nomic-embed-text), переключение конфигом — это опциональное задание проекта.

**п.6. Векторное хранилище (ChromaDB).**
Хранит чанки и их векторы, ищет ближайшие по смыслу. Это «долговременная память» базы — сохраняется на диск, переживает рестарты.

**п.7. BM25-поиск (rank_bm25).**
Классический поиск по точным словам. Это нужно для точечных вопросов («где используется STACK_LIMIT»), где поиск по смыслу бесполезен.

**п.8. RRF-склейка (гибридный поиск).**
Reciprocal Rank Fusion — формула, объединяющая два списка результатов (по словам и по смыслу) в один. Это нужно, чтобы хорошо отвечать на оба типа вопросов сразу, не выбирая «или-или».

## Этап 3. RAG-конвейер (LangGraph + LLM)

**п.9. Ollama + Qwen2.5-3B.**
Локальная нейросеть на машине, без платных API. Это «мозг»: оценивает релевантность и пишет ответы.

**п.10. LangGraph-граф.**
Библиотека-«дирижёр»: описывает конвейер ответа как граф шагов с условиями. Решает, какой шаг за каким и когда повторить поиск.

**п.11. Шаг Rewrite.**
LLM превращает вопрос в хороший поисковый запрос, при повторе — расширяет его синонимами. Нужен, потому что люди спрашивают не теми словами, что написаны в документах.

**п.12. Шаг Retrieve.**
Гибридный поиск (п.7–8) выдаёт топ чанков по запросу.

**п.13. Шаг Grade.**
LLM оценивает каждый найденный чанк: релевантен вопросу или нет (yes/no). Это «корректирующий» шаг, давший имя паттерну Corrective RAG — защита от мусора в ответе.

**п.14. Шаг Generate + retry.**
Если релевантных чанков мало — запрос расширяется и поиск повторяется (максимум 2 раза). Иначе LLM пишет ответ ТОЛЬКО по найденным чанкам и прикладывает источники.

## Этап 4. MCP-сервер

**п.15. FastMCP-сервер и 4 инструмента.**
MCP — протокол, по которому IDE (VSCode Copilot) подключает внешние инструменты к ИИ-агенту. Наши инструменты: index_folder, ask_question, find_relevant_docs, index_status. Описания пишем так, чтобы агент САМ понимал, когда какой звать — это проверяется на сдаче.

## Этап 5. Данные и инфраструктура

**п.16. Демо-база sample_docs.**
Лор вымышленного дополнения «Трон Пепла» для Heroes of Might and Magic III: город Кальдера, герои и их взаимоотношения, существа, артефакты, земли, хронология. ≥500 КБ, 15+ проверочных фактов. Факты — вымышленные (имена, числа, даты мира), их нет в интернете — это доказывает, что ответы из нашей базы, а не из памяти модели. Канон вселенной — только фон.

**п.17. Docker Compose.**
Упаковка: сервер + Ollama + модели поднимаются одной командой `docker compose up`. Нужен, чтобы преподаватель запустил проект без настройки.

**п.18. CI (GitHub Actions).**
Автоматически гоняет линтер и тесты при каждом пуше. Требование задания.

**п.19. Тесты (~40).**
Unit-тесты графа с фейковой LLM, тесты индексатора, e2e тесты MCP-инструментов. Это защита от поломок и критерий «≥10 тестов».

**п.20. Документация.**
README.md и ARCHITECTURE.md (включая секцию про ИИ-инструменты: opencode, superpowers, Context7, GLM 5.3) — заполняю я. REPORT.md — заполняешь ты, диктуя по ходу работы.
